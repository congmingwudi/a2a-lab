# WS25 batch 4 plan critique — Codex

Reviewed the proposed shim-session key change against the current proxy, delegation parser,
authentication middleware, Agentforce client cache, existing isolation tests, Lambda packaging,
and D81. The reported defect is real: `platform_of()` accepts caller-controlled platform text
(`src/interop/delegation.py#L78-L90`), and the proxy concatenates it with the verified subject
using the same `-` that the platform can contain (`src/platforms/agentforce/proxy.py#L61-L75`).
The proposed separate `sub` and `shared` namespaces are the right local boundary, and the shim
bundle does copy the changed module (`deploy/shim/build_zip.sh#L27-L35`). The plan needs the
following corrections before settlement.

## Findings

### 1. Blocker — the proposed function is not injective in the tuple it claims to encode

The plan promises an injective mapping of `(kind, platform, subject)` but computes
`quote(platform or "direct", safe="")` (`build-notes/claude/ws25-b4-plan.md#L47-L59`). That
normalizes two distinct inputs to the same value:

```text
_shim_session_key(None, "alice")      -> shim:sub:alice:direct
_shim_session_key("direct", "alice")  -> shim:sub:alice:direct
```

The literal value is admissible: metadata wins whenever its delegation platform is truthy and is
returned verbatim (`src/interop/delegation.py#L83-L85`). Preserve platform presence explicitly,
for example with disjoint `none` and `value:<encoded>` variants, or narrow the stated invariant
and justify why `None` and literal `direct` are intentionally the same routing identity. Add a
regression for this pair. Because the plan treats platform as untrusted and claims proof by
inspection, silently reserving `direct` is not sufficient.

### 2. Blocker — the planned tests do not require percent-encoding and therefore do not prove the invariant

All four proposed regressions (`build-notes/claude/ws25-b4-plan.md#L80-L95`) can pass with an
implementation that adds only namespace tags and moves the subject before the platform:

- tests 1 and 2 become unequal solely because `sub` and `shared` are different tags;
- test 3 becomes unequal solely because subject-first ordering changes the old `-` collision;
- test 4 also compares `shared` with a verified caller's `sub` namespace, so it passes even if
  the colon in the platform is left unencoded.

Such an implementation still permits a same-namespace delimiter collision when metadata carries
colon-bearing values, for example `(subject="a:b", platform="c")` versus
`(subject="a", platform="b:c")`. The metadata path does not apply the rider regex and returns the
platform string unchanged (`src/interop/delegation.py#L83-L85`). Add a verified-to-verified test
whose two tuples collide without encoding, plus direct assertions that reserved characters in
both subject and platform are encoded (including `%`, so double interpretation cannot alias a
literal escape). Prefer testing the extracted helper directly as well as retaining at least one
real executor/authentication-chain regression.

### 3. Correction — the historical session probe has not gone red

The plan says `readiness_probes.py#L113` "already went red at b3"
(`build-notes/claude/ws25-b4-plan.md#L97-L102`). Running `session_probe()` independently at the
current head succeeds and prints that both callers receive `shim-shared-direct`. The probe places
only caller-asserted `metadata["user_context"]["sub"]` on a request and bypasses the executor that
stamps `verified_subject` (`build-notes/codex/codebase-review/readiness_probes.py#L101-L114`), so
the current proxy correctly treats both as shared-token calls. Keep the historical probe unchanged,
but correct the plan and do not cite it as a red post-b3 reproduction of this delimiter defect.

### 4. Correction — rotating a still-supported shared token does not close the structural exposure

The deploy note says rotating the legacy token closes the exposure without a code deploy
(`build-notes/claude/ws25-b4-plan.md#L124-L126`). Rotation invalidates old or unknown holders, but
any caller given the replacement shared token remains authenticated without a verified subject;
the middleware deliberately accepts that credential (`src/interop/servers/auth.py#L124-L159`).
Revise the note: refusing the shared-token path closes the class of attack, while rotation only
limits exposure to holders of the replacement credential.

   (`tests/unit/test_shim_session_isolation.py#L405-L449`). E1–E5 reproduce the original
   metadata/rider/verified-caller collisions through the executor and real authentication
   middleware (`#L452-L534`). The hermetic twin-env fixture prevents ambient credentials from
   replacing the recording client with a real Salesforce client (`#L105-L114`).

4. **Shared-token residual — documented correctly.** The implementation does not pretend token
   rotation creates identity. Shared-token callers retain the D119-approved platform pool, while
   the disjoint `shared` namespace prevents them from entering a verified subject's session.
   Retirement of Foundry's current shared credential remains operator scope.
