**Verdict: REQUEST CHANGES**

# WS25 batch 3 plan critique — Codex

The plan identifies the right source defects and keeps the batch aligned with
D80, but four decisions remain unresolved in ways that would let the proposed
implementation pass its listed unit tests without satisfying A4, A5, or A11.
Revise the plan before settlement; no implementation should start from the
current version.

## 1. A4's next-tick retry does not retry the failed Salesforce write

`BriefRunner._drive` treats every historical `user.custom_tool_result` as an
answered tool id and skips the matching `agent.custom_tool_use`
(`src/briefs/runner.py#L225-L242`). The current failure path sends exactly such
a tool result after catching the writer exception
(`src/briefs/runner.py#L343-L370`). Reattaching on the next watcher tick will
therefore skip the failed tool call; merely returning `delivered=0` plus an
error can increment the watcher counter, but it does not call Salesforce
again.

Specify a durable replay path. On a later attempt the runner must recover the
failed tool input and invoke `save_brief` again (or persist an equivalent
retryable delivery command) while continuing to skip tool calls that already
succeeded. The result must be per tool call, not only one `delivered` integer
and one error: the system prompt permits one call per account
(`src/briefs/runner.py#L42-L67`), so one scheduled session can partially
succeed. Mark a session `delivered` only when every observed save call has
succeeded; a zero-save/no-error terminated session is not delivery success.

Add a test spanning two watcher ticks that asserts the writer itself is called
twice after the first failure, plus a two-account partial-success test proving
the successful call is not duplicated while the failed call is repaired.
A structured return is preferable to raising because the tool result still
needs to reach the managed session, but it must carry per-call success/failure
data and drive real replay.

## 2. A4 leaves the idempotency boundary undecided and misses the race

D80 explicitly requires a Salesforce uniqueness boundary, and WS25 item 6
records it as part of acceptance (`plan/00-decisions.md#L3356-L3362`,
`plan/07-workstreams.md#L3528-L3532`). The plan's alternative of relying only
on a query-before-insert contradicts that settled scope. Keep
`Research_Session_Id__c` unique and external-id after the duplicate scan; do
not make the metadata change optional.

The proposed sequential “second call inserts nothing” test is insufficient.
Two writers can both observe no brief before either insert. Define the actual
race-safe write path: Salesforce external-id upsert, or insert followed by
handling the uniqueness conflict and re-querying the winning record. Test the
losing-race response and prove it repairs/returns the winning ids without a
second brief.

Task identity also must be settled before implementation. The current Task is
related to the Account by `WhatId` and has no session key
(`src/briefs/salesforce.py#L150-L176`); the brief object has activities disabled
(`salesforce/force-app/main/default/objects/A2ALab_Account_Brief__c/A2ALab_Account_Brief__c.object-meta.xml#L20-L27`),
so “key it off the brief Id via a lookup” is not the current data model. Choose
one queryable, deterministic Task marker/field and list its metadata and
permission-set changes. If full pair idempotency under concurrent writers is
claimed, that Task key also needs an org-enforced uniqueness strategy; an echo
in Subject alone is only a sequential pre-check. Add both partial-pair
directions and a Task race test.

Also define legacy-state eviction. Existing serviced ids have no `at` value
(`src/briefs/__main__.py#L59-L89`), so “evict oldest at” is undefined after
migration. Preserve them deterministically or assign an explicit migration
ordering, and test the 500-entry boundary across mixed legacy/new records.

## 3. A5's trusted Account Id cannot be a loose singular value

One deployment can request multiple accounts and instructs one save call per
account (`scripts/setup_brief_agent.py#L59-L63`,
`src/briefs/runner.py#L64-L67`). The scheduled watcher receives only a session
id (`src/briefs/runner.py#L185-L199`), so it cannot safely thread one
preauthorized `account_id` into every tool call. A model-name mismatch cannot
be merely logged: that can attach one account's brief to another account.

Settle the config as an operator-authored name-to-Account-Id map (prefer a JSON
env value over an inline delimiter, because the current account value itself
contains commas). Resolve each tool call against that map; validate the Id
shape and the retrieved Account, and reject a conflicting binding. When no map
entry exists, use the deterministic name resolver required by D80.

The SOQL tests need adversarial names, not only empty input. Exact-name lookup
must fetch enough rows to detect duplicate exact names, and the optional LIKE
fallback must escape quote, backslash, `%`, and `_` so a non-empty wildcard
input cannot recreate the `LIKE '%%'` problem (`src/briefs/salesforce.py#L107-L126`).
Add those cases and assert no write on ambiguity or binding mismatch.

Finally, the hosted watcher has no `.a2alab/brief.json`; its environment is an
explicit allow-list (`src/briefs/runner.py#L105-L139`,
`deploy/briefs/deploy_briefs.sh#L117-L140`). The plan must include the new
account-map and `A2ALAB_BRIEF_MAX_ATTEMPTS` variables in `.env.example` and in
that deploy script, or the feature will work locally and disappear in Fargate.

## 4. A11's proposed sessionless branch is bypassed by the real A2A server

`AdapterExecutor` always copies `context.context_id` into
`AgentRequest.session_id` (`src/interop/servers/a2a.py#L75-L101`). With the
pinned a2a-sdk 1.1 implementation, `RequestContext` generates a context id when
the inbound message omits one. An executable source check on this checkout
confirmed both `context.context_id` and `message.context_id` are populated for
a sessionless `SendMessageRequest`. Consequently, retaining
`if req.session_id is None` in `AgentforceProxyAdapter`
(`src/platforms/agentforce/proxy.py#L61-L66`) means the proposed
`(platform, subject)` key is never installed on an ordinary hosted A2A call.

For the shim's `session_reuse=True` mode, define whether the proxy deliberately
overrides the SDK context id with the D80 reuse key, or thread a separate
“caller supplied context” signal through the server. Test through
`TokenAuthMiddleware` + the real A2A executor, not only by calling the proxy
with `session_id=None`. The test must prove two verified subjects isolate, two
calls for one subject reuse, and the legacy shared token follows the explicitly
chosen fallback.

A context variable is acceptable for trusted claims if it is set only from
verified JWT claims and reset with its token in `finally` for every request.
Add overlapping ASGI-request tests proving no subject leaks into a concurrent
JWT or shared-token request, including the SDK's background execution path.
Caller-supplied metadata must be overwritten, never preserved, when the trusted
field is stamped (`src/interop/servers/auth.py#L105-L131`,
`src/interop/servers/a2a.py#L75-L101`).

The deployment map is also overstated: `create_a2a_app` is used by the faces
and shim, not by the bridge or console (`src/interop/adapter.py#L38-L55`,
`deploy/shim/handler.py#L41-L55`). The console still needs its own A4 rebuild;
the bridge has no b3 runtime change and should be removed from the deploy list.
