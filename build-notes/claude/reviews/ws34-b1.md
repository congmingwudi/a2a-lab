  the listed semantic IDs and old markers, then re-lists (`src/console/app.py:2207-2358`). The
  verification snapshot puts every surviving or rebuilt row back into one `memories` list
  (`src/console/app.py:2128-2150`). The final hint says "Start fresh deletes this complete
  management listing" (`src/console/static/index.html:5496`). Nothing in the result tells an
  original ID apart from a post-reset row.
- **The quarantine claim holds on all three platforms.** The generic adapter and the Agentforce
  bridge both go through `resolve_customer_memory_scope` (`src/interop/memory.py:163-207`;
  `src/interop/memory_adapter.py:211-231`; `src/bridge/app.py:267-318`). That function drops
  `sourceType: Profile` rows (`src/interop/memory.py:920-929`) and skips the saved-memory merge
  (`src/interop/memory.py:748-753`) whenever a valid generation exists. D121 §1 has the Agentforce
  agent run with native memory disabled. So "not supplied to Claude, OpenAI, or Agentforce" is
  true for a **valid** generation. A malformed one is a different case; see R3.
- **The 360-character cutoff is real.** The model receives `context` in full through
  `_with_context` (`src/interop/memory_adapter.py:265-269`). The browser gets
  `redact(context)[:360]` (`src/interop/memory_adapter.py:314`), and the label "Data 360 memory
  supplied to this agent" has no truncation marker (`src/console/static/index.html:11366-11377`).
- **The duplicate parser is real.** `/api/obs/otel-trace` re-implements span flattening inline
  (`src/console/app.py:5016-5040`). The harvest has its own loop in
  `SalesforceOtelSource._ingest` (`src/observability/salesforce_otel_source.py:233-284`).
  Centralizing the parsing is the right call.
- **The non-goals match the ADRs.** No registration delete matches D107 §1. No erasure claim
  matches D107 §2 and its Consequences. No delete-until-empty loop matches D107 §3 and §7. The raw
  OTLP document staying authoritative matches D73.
- **Numbering, modal pattern, and deploy rules check out.** D122 and WS34 are unused (the last
  entries are D121 and WS33, `plan/00-decisions.md:5462`, `plan/07-workstreams.md:3843`). An
  accessible modal pattern exists (`.dgmodal role="dialog" aria-modal="true"`,

## Required changes

### R1 — Item 2's equality claim is false for real data, so the regression would be written to pass the wrong way

The plan says the new field carries `redact(context)` (plan L62). Its test requires "the complete
redacted evidence field to equal the context actually supplied to the inner agent" (plan L108-109).
It also says the model request and browser evidence "both contain the tail" (plan L70).

The supplied context is never `redact()`-ed. `open_and_read` returns only the owner/profile-masked
text (`src/interop/memory.py:754`), and the adapter sends that to the model unchanged
(`src/interop/memory_adapter.py:265-269`). `redact` rewrites emails, phones, cards and tokens
(`src/interop/memory.py:216-241`). The real POS-bearing graph record **ends** in
`ContactPointEmail[1]{Id,PartyId,EmailAddress}` with the address. The existing fixture pins that
the address reaches the prompt: `tests/unit/test_memory.py:757-758`, asserted at `:767` ("tail of
the record kept"). So on the exact record this batch exists for, the model's tail is the email and
the browser's tail is `[REDACTED_EMAIL]`. The two strings cannot be equal. A test that asserts
equality either fails, or ends up with a fixture that contains no redactable content, which hides
the very difference the card is meant to show honestly.

**Change:**
- Define the field as `redact(supplied_context)`.
- Test `field == redact(context_sent_to_inner)`, plus a separate assertion that the inner request
  carries the unredacted tail.
- Use a fixture that includes the `ContactPointEmail` tail (reuse `POS_ENTRY`).
- Word the label as display-redacted rather than verbatim, for example "Data 360 context supplied
  to this agent (contact details redacted for display)".
- Say exactly what `context_chars` counts: the context block, not the `[a2a-lab memory]` wrapper or
  `IDS_WITHHELD_NOTE` (`src/interop/memory_adapter.py:122-131`).

### R2 — The span glossary has no evidence base yet. Ground it, or it becomes the invention the plan forbids

The plan calls the six names "observed Agentforce span names/types" (plan L87-95). Only `memory_turn`
and `customer_memory` appear anywhere in the repo, and both come from our own Apex/bridge naming
(`tests/unit/test_bridge.py`, `build-notes/codex/agentforce-customer-memory-agent-spec.md`). There
are zero hits outside this plan for `pre_orchestration.guardrail`, `InstructionAdherence`,
`Atlas__GroundednessValidationPrompt`, and `__state_update_action__`. The local store has no
`salesforce-otel` spans (`obs_events` has none for that platform). There is also no OTLP fixture:
`tests/unit/test_console.py` does not exercise `/api/obs/otel-trace` at all.

The official OTel API page the lab cites
(`https://developer.salesforce.com/docs/ai/agentforce/guide/otel-api.html`) defines **no** span
names, types or attributes. It says only that output covers "turns, messages, LLM calls, actions,
metric scores, and feedback". For field definitions it defers to the *Agentforce Session Tracing
data model* and *Generative AI Audit & Feedback data model* Help articles.

So every glossary description is a lab interpretation with no published source. Describing
`InstructionAdherence` as an "evaluation", or a guardrail span as a "policy check", is a semantic
claim drawn from a name. That is the line plan L96-98 itself rules out.

**Change:**
1. **Capture the evidence first.** Before writing the glossary, pull at least one real session
   through the existing route and commit a sanitized OTLP fixture. Strip CRM text and the
   Contact/profile ids; follow the `traces/jev/` "quotes CRM text → gitignored" precedent for
   anything that cannot be sanitized. Cite the hosted trace/session id the fixture came from.
2. **Give every glossary entry provenance.** Record the session it was observed in. Ground its
   description in the Session Tracing / Audit & Feedback data-model docs, or in attributes actually
   present on that span. Mark it in the UI as a *lab interpretation*, separate from the payload.
3. **Fall back for anything unobserved.** A name that is not in the fixture is not seeded; it falls
   through to the honest "no lab interpretation is registered" text (plan L96).
4. **Limit the classification to what is observed.** Only the classes the fixture actually shows
   get registered (orchestration / guardrail-evaluation / memory hook / unclassified, plan L89-90).

### R3 — The new reset evidence needs defined values for the two failure branches the route already has

1. **Verification listing fails.** The route then falls back to the **pre-mutation** listing with
   `complete=False` (`src/console/app.py:2338-2341`). Plan L39-41's "IDs absent after verification"
   and "profile rows quarantined" would be computed against the before-snapshot. That reports 0
   deleted and counts the old rows as quarantined. Both counts must be `null` / "unverified" in
   this branch, never a number, and the UI must say verification did not run.
2. **The marker is malformed.** `_safe_memory_snapshot` sets `profile_memory_suppressed =
   bool(marker)` even when `generation_invalid` is true (`src/console/app.py:2136-2143`). In that
   state every execution seam refuses memory entirely (`src/interop/memory.py:191-193` →
   `memory_adapter.py:232-242`, `bridge/app.py:302-305`). It is not a valid-generation quarantine
   in which "only this generation's conversation context is eligible"
   (`src/console/static/index.html:5486-5489`). Key the **Quarantined profile rows** heading (plan
   L43-45) on `profile_memory_suppressed && !generation_invalid`. Give the invalid-marker state its
   own copy, "memory is suppressed for all agents until a valid generation exists" (D107 §2), and
   pin both in tests.

## Advisories (fix in the build; not blocking)

- **A1 — Problem statement 1 understates what exists.** D107 §7 already decided "the management
  panel continues to show re-materialized profile rows … and explains that they are quarantined"
  (`plan/00-decisions.md`, D107 §7). The hint at `src/console/static/index.html:5486-5489` ships
  that. The defect is the contradicting final hint (`:5496`) and the undifferentiated
  post-mutation result, not a missing explanation. Frame D122 as refining D107 §7's presentation so
  the ADR log does not read as two competing contracts.
- **A2 — Do not let the new counts silently change `ok`.** By D107 §3, a fresh reset is verified
  when the exact new marker re-lists and every delete completed without error, and rebuilt rows do
  not fail it (`src/console/app.py:2346-2357`). If the implementer wants "original IDs still
  present" to affect `ok`, that is an ADR-level change to D107 §3. Otherwise state in D122 that
  the counts are evidence only.
- **A3 — Point the harvest at the same parser.** `_ingest`
  (`src/observability/salesforce_otel_source.py:233-284`) writes `obs_events` rows with the same
  `_span_type`/`_span_summary`. If only the live route moves to the new helper, live and harvested
  rows can drift. Either share the helper or scope `_ingest` out explicitly.
- **A4 — Watch OTLP edge cases in the parser.**
  - Compute duration from the integer nanosecond strings; `_nano_to_iso`
    (`src/observability/salesforce_otel_source.py:68-76`) is display-only and float-based.
  - OTLP/JSON `status.code` may be an int or a `STATUS_CODE_*` string, and the current display is
    `message or code` (`src/console/app.py:5037`). Pin both forms.
  - Flatten `bytesValue` as well: `_attr_value` (`src/observability/salesforce_otel_source.py:79-91`)
    currently returns `None` for it, so the "flattened attributes" view would silently drop it.
  - Pin `kvlistValue`/`arrayValue` nesting (plan L111) in the same test.
- **A5 — State the bound and check the masks over the full string.**
  - The complete context is up to `GRAPH_LIMIT` 4000 + body 4000 + up to `MAX_SAVED` 20 saved lines
    (`src/interop/memory.py:805`, `:897`, `:675`). It rides response metadata into trace JSONL and
    Aurora on every memory turn. State that bound in D122.
  - Add an assertion that the **full** field contains neither the raw owner id nor a graph profile
    id. Today that guarantee is only exercised by the 360-character preview test
    (`tests/unit/test_memory_adapter.py:176`). D118's Contact-id rule now applies to roughly 25×
    more text.
- **A6 — Docs.** Plan L122-123 covers `plan/09`. `plan/05-observability.md:97-98` also narrates the
  Session Trace export and should gain the per-span drill-down sentence, since the Details pane
  will cite it. Write the WS34 item lines in `plan/07` as `N. ✅` / table rows so `jira_sync.py`
  imports stories, not a childless epic (CLAUDE.md, D58).
- **A7 — Smoke plan.** "Open Explain on … an unknown/generic span" (plan L127) only works if the
  R2 fixture shows which observed spans are deliberately left unregistered. Name one in the smoke
  checklist once R2 is done.

## Disposition

Items 1 and 3 are sound in shape. Item 2 is sound once the equality contract in R1 is corrected.
R1 changes a test contract, R2 changes where the glossary's facts come from, and R3 defines two
failure-path values. All three are small plan edits, and none reopens scope. Codex may answer them
in place, and I expect to PASS a plan that adopts them.
