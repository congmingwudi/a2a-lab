### Findings

**R1-1 (blocking: evidence contract). Scenes 6 and 7 contradict D115 as it stands at the branch
head.** `5a54694`, committed two minutes after the build, adds the D115 correction of 2026-11-06
15:18Z: "the real-time graph IS served when `owner_id` is the Contact id". With arm B's configuration
restored, GetContext returned the full `Customer360` CRM record. The earlier "not served" result came
from two failures that hid each other: the wiped configuration, and the faces' owner mapping, which
resolves to the memory pipeline's own Individual. The tour still teaches the superseded reading:
- `index.html` scene 6, node "CRM graph controls": "The current CRM-backed controls returned no CRM
  record for the resolved profile."
- Scene 7, node "Open": "… CRM graph identity alignment". The cause is now diagnosed; the remaining
  work is a pending identity-contract ADR plus a full-configuration PATCH, not an open question.
- `plan/20-console-presentation-mode.md` evidence contract: "the current CRM-backed profile mismatch".
- The plan's wording "surviving CRM graph control … do not rely on the earlier arm" points the wrong
  way now. Arm B is the arm that serves.

D116 limits every scene to the current measured state, and a presenter following scene 6 today would
leave the audience thinking the CRM graph does not work. Fix: scene 6 should say that attached
graphs, including the operator-built real-time CRM graph, are served when keyed by the customer's
Contact id. The live demo receives no CRM record because the live registration has no graph attached
and the faces send the pipeline's own Individual. Changing that is a pending D91/D104
identity-contract decision, so the tour makes no live CRM-graph claim. Then move scene 7's "Open"
cell to the actual open items, and pin the new wording in
`test_agent_memory_presentation_mode_is_eight_scene_evidence_only_handoff`.

**R1-2 (should fix: focus loss). The presentation branch of `renderMain` ignores its own render
cache.** It sets `mainKey = \`memory-presentation:${scene}\`` but never compares it before
`el.innerHTML = memoryPresentationHtml()`, so every unforced `renderMain()` rebuilds the stage.
`connectStream`'s `onHop` calls `renderMain()` whenever `selected === hop.trace_id`, and `selected`
still holds the trace id of the experiment the presenter came from. So if the presenter enters the
tour from an experiment while its turn (or a platform-initiated leg of it) is still landing, each
hop replaces the DOM. Keyboard focus on a scene-rail button or the stage drops to `<body>`, and
scrolling inside the stage resets. Fix: return early when `!force && mainKey === key`, matching the
other views. `setMemoryPresentationScene` and `loadConfig` already pass `force`.

**R1-3 (should fix: keyboard). Escape is not guarded for text entry, but the arrow keys are.**
The capture-phase listener exits the presentation on any unconsumed Escape. Arrow keys skip
`input, button, select, textarea, dialog`, but Escape skips only popovers, diagrams and fullscreen.
The header stays visible during presentation, so the Lab Guide drawer and the user/sign-in panel
(which `requireSignIn()` opens from scene 8 after a session expiry) can both have focus inside a
text field. Neither has its own Escape handler: the only others are the decision popover, the
diagram modal and the figure fullscreen. Pressing Escape in either field leaves the tour, and
`goBack`'s focus restoration pulls focus out of the field onto the launcher. Fix: ignore Escape when
`ev.target` is a text-entry control, or when it is inside the guide drawer or the user panel.

**R1-4 (should fix: evidence honesty). The browser JSON reports matrix rows as passed that the
harness does not exercise.** Compared with the plan's interaction matrix:
- **Section entry.** The harness clicks `#memory-presentation-section`; the matrix calls for keyboard
  focus followed by Enter.
- **Scenario shortcut.** Neither the card button `memory-presentation-<name>` nor the experiment-tab
  shortcut `memory-presentation-tab-<name>` is ever launched, so focus return to those invokers is
  untested.
- **Live handoff.** The run stays on the Maya default, so the promise to preserve a non-default valid
  customer (select Jordan, enter, hand off, still Jordan) is untested.
- **Auth change.** The harness clears `labUser` and checks that suppression *persists*. It never
  checks that the saved `a2a-side-open` preference is restored after leaving.
- **Motion and accessibility.** `prefers-reduced-motion` is never emulated, and the live-region text
  is never read.

Then `design-qa.md` ticks those items. Either exercise them or narrow the JSON keys and checklist to
what ran. Screenshots and passes for the rows that did run are credible.

**R1-5 (nit).** `design-qa.md` was committed at the repo root. The plan says "Record browser
evidence and design QA under `build-notes/codex/`", and the notes cite it without a path. Moving it
to `build-notes/codex/` keeps it next to its screenshots. It is not in the image either way, since
the Dockerfile copies only `README.md CLAUDE.md` from the root.

**R1-6 (nit, existing behaviour).** Exit from a tour opened on the landing page can return to a
stale view. `pushNav()` does nothing while `view` is null, and `goHome()` never clears `navStack`.
So landing → experiment A → experiment B → home → Present → Exit pops A instead of returning to the
landing page. The same goBack behaviour exists for other views, but "Exit presentation" promises a
return. Either clear the stack in `goHome()` or record `{view: null}` on entry. Non-blocking.

**R1-7 (nit, accessibility).** The `role="status"` live region sits inside `#detail`, which is
rebuilt on every scene change and filled one animation frame later. Some screen readers (VoiceOver
in particular) skip announcements from a live region that was just inserted. Moving focus to the
labelled stage reads the title anyway, so this is belt-and-braces: hoisting one persistent status
node outside `#detail` makes the announcement reliable. Separately, the stage and the outer
`<section>` share the same accessible name (`aria-labelledby="memory-present-title"`), which gives
two landmarks one name.

**R1-8 (nit, test).** The new test is followed by one blank line instead of two before
`test_config_exposes_safe_customer_personas_without_profile_ids`. `html.count("openMemoryPresentation(") == 3`
is a source-string count that breaks if a fourth call site is added for a legitimate reason. Prefer
asserting the three launcher ids.

### Non-blocking notes (none gate this PASS)

- **R2-n1 (format).** The new ``assert 'const key = `memory-presentation:${scene}`' in html`` line
  should use double quotes per `ruff format`. It rides with the file's existing format drift.
- **R2-n2 (test strength).** The reduced-motion probe reads `transitionDuration`/`animationDuration`
  on `.memory-present-stage`. The presentation CSS declares no transition or animation of its own,
  so the probe would read `0s` without the `prefers-reduced-motion` rule too. It proves the
  emulation matched and nothing on the stage animates, not that the rule is load-bearing. A
  stronger probe would target an element that animates under `no-preference`, or the design-QA
  line would say the mode has no motion to suppress.
- **R2-n3 (a11y, minor).** The persistent status node is never cleared on exit. Re-entry always
  starts at scene 1, so exiting from scene 1 and re-entering writes identical text, and some
  screen readers skip an unchanged atomic region. Focus moves to the stage labelled by the scene
  title, so the title is still read. Clearing the node in `exitMemoryPresentation` would make
  this airtight.
