# ws33-b1 critique: Agentforce as the third shared-memory participant

**Critic:** Claude Code · **Round:** 0 · **Plan:** `build-notes/codex/ws33-b1-plan.md` · **Spec:** `build-notes/codex/a2alab-agentforce-shared-memory-agent-spec.md`

The plan assumes the Apex → bridge `POST /memory/turn` route reaches the same memory as the Claude and OpenAI `MemoryAdapter` seam. It addresses the same registration and owner. But once the exhibit's "Start fresh" has run, it reads and writes a different conversation. It also has no owner allow-list, and it gives the console nothing to show as memory evidence. Four of the ten acceptance scenarios would fail or be unprovable as written. The fixes are concrete and small, but they move work into `src/bridge/app.py` and into a bridge deploy. That contradicts three statements in the plan: no new backing logic (`ws33-b1-plan.md:39-40`), no faces rebuild (`:59-60`), and a console-only deploy (`:114`).

## Findings

### F1 (blocking): the bridge route ignores the customer-memory generation, so Agentforce diverges from Claude/OpenAI after Start fresh

- `src/bridge/app.py:225-234` calls `open_and_read` and `write_turn` without a `conversation_id`. `src/interop/memory.py:152-153` then falls back to `owner_conversation(owner)`, the owner's long-lived conversation.
- `MemoryAdapter` does more, when a customer key is present (`src/interop/memory_adapter.py:208-224`):
  - it lists the generation category;
  - it switches to `generation_conversation(owner, marker)`;
  - it turns off saved memories and profile context for that generation (`:266-267`).
- The exhibit promises exactly that behaviour: after Start fresh, "profile-wide rows ... are quarantined from agent prompts. Only conversation context produced inside the new generation is eligible for recall" (`config/scenarios.yaml:83-88`).
- **Failure:** spec acceptance 1 opens with "Start fresh for Maya" (`a2alab-agentforce-shared-memory-agent-spec.md:174-175`). After that, Claude writes into the generation conversation and Agentforce reads the owner conversation plus quarantined saved and profile rows. Scenarios 1, 2, 3 and 5 (`:174-183`; plan `:109-110`) then measure two different memories, or show pre-reset facts as recall.
- **Correction:**
  1. Move `MemoryAdapter`'s generation resolution into one shared helper in `interop.memory`, so the two seams cannot drift. Call it from `/memory/turn`, passing `conversation_id` and the `include_saved_memories` / `include_profile_context` suppression.
  2. Add bridge unit tests to `tests/unit/test_bridge.py` / `tests/unit/test_memory.py`.
  3. Add `src/bridge/app.py` to the plan's files, and a bridge **full rebuild** (`deploy/bridge/deploy_bridge.sh`) to Items 3 and 7.
  4. Remove "no faces rebuild is needed" (`ws33-b1-plan.md:59-60`) as far as it implies nothing else ships.

### F2 (blocking): the stale-generation guard is lost for the new target

- `src/console/app.py:3453-3458` forwards `memory_customer` and `memory_generation` only when `chosen_memory` is true, and that is only set under `memory_toggle` (`:3393-3400`).
- The plan removes the toggle for this scenario (`ws33-b1-plan.md:80-83`). So `memory_generation` never reaches the target.
- `MemoryAdapter` refuses a chat that started under an older generation (`memory_adapter.py:227-238`). The Agentforce path has no equivalent:
  - the cached Agentforce session survives a rotation;
  - Apex keeps threading the old memory session id (`src/bridge/app.py:211-214`; `.agent` `set @variables.memory_conversation`).
- **Correction:**
  1. Forward `memory_customer` and `memory_generation` for target-managed scenarios, independent of the generic toggle.
  2. Make the Item 3 session fingerprint `(owner, generation)`, not owner alone.
  3. On a mismatch, `end_session` the cached Agentforce session and return the same `stale_memory_generation` error shape (`memory.py:62-68`).
  4. Add tests for rotate-mid-chat and for a stale generation being refused before any Agent API message is sent.

### F3 (high): "memory evidence renders" and "joined trace evidence" have no data source

- `memoryBadgeHtml` renders `memory: no report` whenever `resp.metadata.memory` is absent (`src/console/static/index.html:11316-11317`). Only `MemoryAdapter` emits it (`memory_adapter.py:315-337`).
- `AgentforceClient.ask` returns only `agent_session_id` (`src/platforms/agentforce/client.py:244`). The Apex action's `context` / `ok` / `traceId` outputs stay inside Agentforce.
- `A2ALabMemoryTurn` creates its own random trace id (`A2ALabMemoryTurn.cls:81,90`). So the bridge and tenant hops are recorded under a trace id the console never selected.
- Item 5's test "memory evidence, attribution, and Agentforce session-trace link render correctly" (`ws33-b1-plan.md:85-86`) and Item 7's "joined Agent API/bridge/memory trace evidence" (`:110-111`; spec `:190-191`) have no mechanism behind them.
- **Correction:** name the join key and how the console gets evidence. The clean option:
  - add an optional correlation input to `A2ALabMemoryTurn` (for example the lab session id, carried in an External session variable set at session creation);
  - have the bridge stamp its hop with it;
  - have the console look up that hop to build a `metadata.memory` block for the new target, with a target-managed badge variant.

  This is an Apex change plus its test, a **production** deploy needing ≥75% coverage (CLAUDE.md, "Salesforce side"). It contradicts "no new Apex" (`ws33-b1-plan.md:39-40`), so record it in D121. If the change is rejected, downgrade the Item 5 and Item 7 claims to "correlated by owner/time" and drop "joined".

### F4 (high): the bridge trusts any `agent_id`/`owner_id`, and the "safe default owner" still writes to the shared registration

- `src/bridge/app.py:205-207` only checks that both fields are present.
- D115 established that, for this caller, the owner sent *is* the isolation boundary (`src/interop/memory.py:303-308`).
- The bridge task has no `A2ALAB_MEMORY_CUSTOMER_MAP` (`deploy/bridge/deploy_bridge.sh:78-85,248,287`), so it cannot check owners. The plan's "trusted backend owner binding" (`ws33-b1-plan.md:21`) is enforced only in the console.
- The concierge's safe default `a2alab-persona-default` (`A2ALab_Memory_Concierge.agent:23`) would be sent to `A2ALab_Memory_Case`. D115 records that the memory API creates an Individual for an owner the first time it opens that owner's conversation (`plan/00-decisions.md:5155-5157`). So a preview or misconfigured session plants a junk owner in the shared registration.
- **Correction:**
  1. Allow-list `agent_id` at the bridge (this route serves only `A2ALab_Memory_Case`).
  2. Allow-list `owner_id` against the values of `A2ALAB_MEMORY_CUSTOMER_MAP`, shipped to the bridge task.
  3. Return `ok:false` **without a tenant call** for anything else.
  4. Change the Item 2 test "Preview without an owner must stay outside Maya/Jordan" (`ws33-b1-plan.md:43`) to assert that no tenant call is made.

### F5 (medium): Item 3 owner resolution must reuse `owner_of`'s verified-identity checks

- `owner_of` (`memory_adapter.py:88-114`) resolves the map only for a **verified, non-machine** `user_token`. Without a customer key, it falls back to `A2ALAB_MEMORY_OWNER_MAP`.
- Item 3 says only "resolve `metadata.memory_customer` through the existing server-side map" (`ws33-b1-plan.md:51-53`).
- **Correction:**
  1. Reuse `owner_of`, or a shared core of it, so the D115 boundary holds.
  2. Require a customer key for this target: no owner-map fallback.
  3. Add tests for an unsigned caller and a machine-role caller.
- Also make the missing-variable failure (`ws33-b1-plan.md:70-71`) explicit in code. `_expand_env` turns an unset `${SF_MEMORY_AGENT_ID}` into `""` (`src/interop/registry.py:38-44`). `from_target` would then build `/agents//sessions` (`client.py:97-107,157`). Raise in `from_target` when `agent_id` is empty.

### F6 (medium): the delivery record misses the revived bridge verb and the identity preflight

- `plan/09-deployment-map.md:346-375` and CLAUDE.md's plan/18 sentence ("that route is historical until re-registered") both describe `/memory/turn` as historical. This batch revives it under a different registration, so both must be rewritten in the same change. The bridge's L6 row needs updating too.
- Item 1 lists `plan/09` (`ws33-b1-plan.md:18-19`) but not this change; CLAUDE.md is not listed.
- `scripts/identity_preflight.py:48-60,375` checks each caller's Agent API agent id (D37/F6). Add `SF_MEMORY_AGENT_ID` there and to `.env.example` / env-contract tests.

### F7 (low): hook latency and partial-failure behaviour are unmeasured

- The hook runs start, GetContext, saved-memory listings, ingest and close in series (`src/bridge/app.py:226-236`; `memory.py:691-694,721-725`), behind a 20 s Apex timeout (`A2ALabMemoryTurn.cls:28`). F1 adds one more list call.
- `MemoryAdapter` caps each phase at 8 s (`memory_adapter.py:82,182-186`); the bridge has no cap.
- **Correction:**
  - cap the bridge phases the same way;
  - record hook latency in `plan/03-results.md`;
  - test the case where Apex times out but the bridge finishes the write (stored without recall).
